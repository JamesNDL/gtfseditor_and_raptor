# Journey router build plan (Java, RAPTOR, capacity aware)

Written 13 Nov 2026. Phase 0 (the empty project) was built the same day; its findings are in section 14. Phase 1 (the timetable loader) was built on 15 Nov; its findings and measurements are in section 15. Phase 2 (the search) was built the same day; see section 16. Its results were then checked and improved for quality and speed on journeys inside the Opal area; see section 17, which replaces the speed figures in section 16. Its journeys were then compared with the TfNSW trip planner's; see section 18. Phase 3 (the service) was built on 17 Nov; see section 19. Phase 4 (capacity and bulk requests) was built the same day; see section 20. The benchmark harness, road routing and the website's use of the router are not built.

## 1. Summary

Build a standalone Java service, `services/router`, that answers "how do I get from A to B at this time" on the public transport timetable and, separately, by car. It reads the GTFS zip the editor already exports, including the two capacity files. It runs as an HTTP service or as a Java library inside another program.

Main recommendations:

| Topic | Recommendation |
|---|---|
| Algorithm | Plain RAPTOR first, with one shared search loop. Range RAPTOR added later for "all options in the next hour". No McRAPTOR in the first version. |
| Capacity | A per-request switch with three settings: `off`, `check` (respect current loads) and `assign` (respect loads and add this passenger to them). A full trip is skipped at the stop where it is full. |
| Data in | GTFS zip first, because it works for any application. Reading PostGIS directly comes later, to avoid the multi-minute export. |
| Transfers | Generated by the router at load time from stop distance, plus the feed's station pathways. |
| Road routing | GraphHopper embedded as a Java library with an OpenStreetMap extract for NSW, in its own module that can be switched off. |
| Service | Javalin (a small web framework) on Java 25, built with Gradle, one Docker image. |
| Website | The browser calls the existing Node API, which forwards to the router. |

Estimated size of the first usable version: about 4 to 5 weeks of focused work (phases 0 to 6 below).

## 3. Scope

### In the first usable version

1. Load a GTFS zip (the editor's export or any ordinary feed) into memory.
2. Answer a single journey query: origin, destination, departure time, capacity setting.
3. Answer a bulk request of many origin-destination pairs.
4. Capacity awareness with the three-way switch, and a benchmark that compares the settings.
5. A separate road endpoint that returns the driving time, distance and path.
6. Health, metadata and reload endpoints.
7. Use as a library from Java with no web server.
8. A Docker image and an entry in `docker-compose.yml`.

### "Done" means

- All correctness tests pass (section 9), including the rule that `check` with empty loads gives exactly the same answers as `off`.
- The NSW weekday loads on the development machine within the memory budget in section 5.
- The benchmark report exists and shows `off` against `check` against `assign` on the same queries.
- The Node API can forward a journey query and a road query, and the web app can show both results side by side. A minimal panel is enough.

### Explicitly later

- **The tap-data simulator.** Loading tap-on/tap-off records, moving people through the network in time order, queues at stops, dwell times that depend on crowds. The router is built so the simulator can drive it (section 4.4), but none of the simulator is in this plan.
- Arrive-by queries, real-time delays, fares, accessibility-only routing, bike and park-and-ride.
- Crowding as a discomfort penalty (section 4.3).
- Several service days at once (journeys that cross into the next day's timetable).

## 4. Algorithm

### 4.1 Which RAPTOR

| Variant | What it gives | Cost | Verdict |
|---|---|---|---|
| Plain RAPTOR | The earliest arrival for each number of changes, for one departure time. | Fastest and simplest. | **Build first.** It is what bulk routing of tap records needs: each record has one departure time. |
| Range RAPTOR (rRAPTOR) | Every sensible journey leaving within a time window. | Runs the plain search once per departure in the window, reusing earlier work. Roughly 3 to 10 times one plain query for a one-hour window (estimate). | **Add after the first version**, for the website ("options in the next hour") and to speed up bulk runs without capacity. It reuses the plain search loop, so it is a small addition. |
| McRAPTOR | Trade-offs between several criteria, such as time against crowding or walking. | Each stop holds a set of labels instead of one number. Typically several times slower and much heavier on memory. | **Not now.** Only needed if crowding becomes a discomfort penalty rather than a hard limit. |

Plain RAPTOR already returns the trade-off between arrival time and number of changes, because it works in rounds (round k = journeys with k rides). The response can therefore offer "fastest" and "fewer changes" without McRAPTOR.

Settings fixed for the first version: at most 8 rides per journey (configurable), one walk between consecutive rides, and target pruning (stop exploring anything that cannot beat the best arrival found so far).

### 4.2 Capacity model

**What is stored.** One number per stop time: the passengers on board as the trip leaves that stop. For the weekday that is 2 million numbers, 8 MB. One capacity per trip, taken as `seated + standing` from the two editor files, times a configurable factor (default 1.0). Trips with no vehicle row get a default per mode, and the metadata endpoint reports how many.

Loads live in a separate object, the **load state**, not in the timetable. The timetable never changes after loading; a load state is a sheet of numbers laid over it. That separation is what makes the switch cheap and the comparison fair.

**Denied boarding.** When the search looks for the first trip it can catch at a stop, it skips any trip whose load leaving that stop has reached capacity, and takes the next one on the same pattern. Nothing else in the algorithm changes. With loads held fixed during one query, the answer is still exactly the earliest arrival: waiting at a stop is always allowed, so arriving earlier is never worse.

**The three settings.**

| Setting | Reads loads | Writes loads | Use |
|---|---|---|---|
| `off` | No | No | Ordinary journey planning; the speed baseline. |
| `check` | Yes | No | "What would this person do given how full things are?" |
| `assign` | Yes | Yes | Bulk runs: each routed passenger is added to the trips they ride, so later passengers see fuller vehicles. |

**Assigning many passengers.** Order matters, and the plan should be honest about it:

1. Requests are sorted by departure time and handled in time slices (default 5 minutes).
2. Within a slice, passengers are routed in parallel against the loads as they stood at the start of the slice.
3. They are then committed one at a time in a fixed order. A commit adds 1 (or the group size) to every segment the passenger rides.
4. If a commit would push any ridden segment over capacity, that passenger is not committed. That boarding is marked as blocked for them and they are routed again. After 3 failed tries (configurable) they are reported as `stranded` with the reason.
5. The result is the same every time for the same input, whatever the thread count.

This is first come, first served by departure time. It is not an equilibrium assignment, and it is not a faithful simulation. A passenger who starts later but boards further up the line would, in reality, get the seat ahead of someone boarding downstream; here whoever was processed first holds it. Getting that right needs boardings processed in true time order, which is the simulator's job. The first version reports how many passengers were re-routed and stranded so the size of the approximation is visible.

An optional second pass is included in the design but off by default: empty the loads, re-run everyone against the loads from the previous pass, and repeat until fewer than a set share of passengers change route (default 1%) or 5 passes have run. I recommend not building it until the simulator shows it is needed.

**Loads before tap data exists.** Two sources: a synthetic demand generator in the benchmark module (random pairs weighted by how much service each stop has), and an upload of background loads as CSV (`trip_id, stop_sequence, load`).

### 4.3 Crowding penalties

A penalty (for example, time on a standing-room-only vehicle counts 1.5 times) makes "best" no longer the same as "earliest", so plain RAPTOR stops being exact and McRAPTOR is needed. Recommendation for now:

- Report crowding on every leg of every result: the highest load, the capacity and the load factor.
- Offer a "comfortable capacity" option: treat a trip as full at a chosen share of capacity (for example seats only). This is still a hard limit, so it costs nothing extra.
- Leave true penalties to a later phase, as a two-criteria McRAPTOR that reuses the same timetable arrays.

### 4.4 Hooks for the simulator

The simulator will route a passenger, move them, and re-route them when they cannot board. The router supports that from the start with two request options: start from a given stop at a given time, and a list of blocked boardings (trip and stop) to avoid. Both are needed anyway for step 4 of the assignment.

### 4.5 One code path, fair comparison

- There is one search class. The capacity test is a single line in the "find the first catchable trip" step, guarded by "is there a load state".
- `off` passes no load state. `check` and `assign` pass one. No duplicated algorithm, no separate "fast" build.
- The benchmark runs four cases on the same queries, same timetable, same threads, same warmed-up Java process, interleaved so that neither case benefits from running last:

| Case | What it isolates |
|---|---|
| `off` | Baseline. |
| `check`, empty loads | The cost of the test itself. Answers must equal `off`. |
| `check`, realistic loads | The cost of skipping full trips and searching further. |
| `assign` | The above plus writing loads and re-routing. |

## 5. Data structures and memory

Everything is flat arrays of primitives, indexed by small integers assigned at load time. No object per stop time.

| Structure | Layout | Weekday size (estimate) |
|---|---|---|
| Stops | Index 0..n-1 for boardable stops in use; arrays for latitude, longitude, parent station; ids and names in one byte block | 89,444 stops; about 10 MB with names |
| Router patterns | Trips with the same stop sequence and the same pick-up/set-down flags, split further so no trip overtakes another. Per pattern: offset into the pattern-stop array, stop count, offset into the trip list, trip count | Starts from the editor's 18,167 patterns; expect 20,000 to 25,000 after splitting (to be measured) |
| Pattern stops | One `int[]` of stop indexes, pattern after pattern | 503,217 entries, 2 MB |
| Stop times | Two `int[]` (arrive, depart), in seconds from the start of the service day, ordered by pattern, then trip (sorted by departure), then stop. The time for trip t at position p is at `patternOffset + t * stopCount + p` | 2.0 million entries, 16 MB |
| Pick-up/set-down flags | One byte per pattern stop | under 1 MB |
| Stop to patterns | For each stop, the patterns serving it and the position within each | 4 MB |
| Transfers | For each stop, a block of (target stop, walk seconds) pairs | 6 to 15 MB, depending on radius (to be measured) |
| Trip data | GTFS trip id, route, capacity, stay-aboard link | about 6 MB |
| Load state | `int[]` parallel to the stop times | 8 MB each |
| Per-thread search state | Arrival time per stop per round, plus how each stop was reached; reset by a version stamp, not by clearing | about 12 MB per worker thread |

Budget for one loaded weekday:

- Timetable: under 100 MB of heap.
- Service with 8 worker threads and two timetables held (baseline plus one scenario): heap limit 768 MB, whole process under 1 GB, without road routing.
- Loading reads the zip as a stream and must not hold the CSV rows as objects. Peak during load should stay under 1 GB.

These are estimates from the row counts. The first load of the real export will confirm or correct them, and the metadata endpoint reports the measured figures.

## 6. Data input

### 6.1 Zip, database, or both

| Option | For | Against |
|---|---|---|
| GTFS zip from the editor's export | Works for any feed and any application. Already carries capacity. Already verified by `npm run export:check`. No database knowledge in the router. | The export takes 2 to 5 minutes per scenario, most of it shapes the router does not need. |
| Read PostGIS directly | Fast: the baseline never changes, so it can be read once and a scenario's changes added on top in seconds. | Ties the router to this schema. Must repeat the scenario visibility rule exactly. |

**Recommendation: both, in order.** The zip first; it is the standalone contract and the test input. Both sit behind one "timetable source" interface that produces the same in-memory model.

Two cheap improvements to the zip path, both small changes in the Node API (to be agreed, not part of the router itself):

- An export option that leaves out `shapes.txt`. The router does not use it. This should cut most of the export time (to be measured).
- After building, the router saves its arrays to a file keyed by a fingerprint of the zip. A restart then loads in about a second instead of re-reading the zip.

The database reader is a later phase. It would use the same rule as `visible()` in `apps/api/src/scenarios.ts`: baseline trips not listed in `scenario_removed` up to the scenario's `head`, plus the scenario's own trips with `created_edit <= head` and no earlier `removed_edit`. Capacity would come from the `trip_vehicle` view joined to `vehicle_types`.

### 6.2 What the loader does with the editor's export

- Drops stops that no trip uses (the export lists about 171,000; about 89,000 matter).
- Reads `calendar.txt` and `calendar_dates.txt` and takes a service date. For the editor's export there is one service and one date, so this is automatic.
- Honours `pickup_type` and `drop_off_type`, so run-through stops cannot be boarded or left.
- Treats two trips sharing a `block_id` as a stay-aboard pair. First version: a zero-time change at the same stop is allowed, and the result marks the two legs as `stayAboard` so it is not shown or counted as a change. Later: handle it inside the search so it does not use up a round.
- Reads the two editor files if present. If absent (an ordinary GTFS feed), capacity falls back to a per-mode default from configuration and the metadata says so.
- Reads `transfers.txt` if a feed has one.

### 6.3 Transfers and walking links

The editor has none between nearby stops, so the router generates them at load time:

1. **Inside stations:** build the pathway network (platforms, entrances, walkway nodes) and find the shortest time between each pair of platforms of the same station. Needed because most pathways do not join platforms directly.
2. **Nearby stops:** every pair within a radius (default 400 m straight line). Walk time = distance x 1.3 (detour factor) / 1.2 m/s, plus 30 seconds. Found with a simple grid over the stops; no database needed.
3. **Same parent station without pathways:** as rule 2, with a 60-second minimum.
4. A cap on links per stop (default 40 nearest) keeps the table bounded in dense areas.

All figures are configuration. They are assumptions, not sourced values, and the metadata endpoint lists them.

When the editor gains its own editable transfers (already on its plan), it should export them as `transfers.txt` and the router will prefer them. Once road routing is in (section 7), walk times can come from the footpath network instead of straight lines.

**Getting to and from the network.** A query may give a stop id, a station id (all its platforms are used) or a coordinate. For a coordinate, the first version walks in a straight line to every stop within 800 m, with the same speed and detour factor.

### 6.4 Times and the service day

- All times are seconds from the start of the service day, exactly as the editor stores them (`arr`, `dep`). Values above 86,400 are normal.
- A request gives a time as seconds or as `HH:MM:SS` up to `36:00:00`. So 00:30 after midnight on the same service day is `24:30:00`. The API documents this and the Node proxy can convert clock times for the web app.
- One service day is loaded at a time. A journey that would need tomorrow's first train finds nothing. This is a stated limit of the first version.

### 6.5 Scenarios and reloads

- The router holds several timetables, each under an id chosen by the caller, for example `b1` for a baseline and `b1-s7` for scenario 7.
- A reload builds the new timetable beside the old one and swaps it in when ready. Queries keep running on the old one until then. A failed build leaves the old one in place.
- At most 2 timetables are kept by default (the least recently used is dropped), because of memory.
- **Knowing when a scenario has changed.** `head` alone is not enough (see section 2). Recommended version key: scenario id + `head` + the `created_at` of the edit numbered `head` in `scenario_edits`. The Node API computes it, compares it with the version the router reports, and asks for a reload when they differ.
- Capacity edits are not covered by that key, because vehicle types are shared and carry no change time. Default: a "refresh journey planner" action in the editor forces a reload. A change-time column on `vehicle_types` would close the gap later.
- Load states belong to one timetable version. A reload discards them and says so in the response.

## 7. Road routing

### 7.1 Options

| Option | For | Against |
|---|---|---|
| **GraphHopper embedded** (Java library, OpenStreetMap extract) | Same language and process; no extra container; car, foot and bike profiles from one graph; also usable as a library by embedders. As far as I know the core is Apache 2.0 licensed and can avoid areas per request through its "custom model" feature. | Adds memory and a one-off import step. I have not checked the current release's licence, Java requirement or which features are in the open-source part (its matrix service has been commercial-only in the past). **Verify before committing.** |
| Self-hosted OSRM (Docker) | Very fast. The editor already speaks its API, so `ROUTER_URL` could point at it unchanged. | A second service to run. Preparing the data is memory hungry. Cannot be told a road is closed per request, which is the editor's current pain. |
| Self-hosted Valhalla (Docker) | Can avoid areas per request and has time-of-day speeds. `PLAN.md` originally named it for closures. | A second service, in C++, with a different API from the one the editor uses today. |
| Keep the public OSRM demo server | Nothing to build. | Not for real use: shared, rate limited, sends coordinates to a third party, and unsuitable for bulk. |
| Write our own | Full control. | Weeks of work to match a mature engine. Not recommended. |

### 7.2 Recommendation

**GraphHopper embedded, in its own module (`router-road`) behind a small interface**, switchable off in configuration. Reasons: one Java service to deploy, the same engine can later supply walking times, and it can route around closed areas.

If memory proves too tight on the development machine, the same jar can be started a second time in "road only" mode as a separate process, with no code change. If the licence or feature check fails, the interface allows OSRM or Valhalla behind it instead.

### 7.3 Cost (estimates, to be measured)

| Item | Estimate |
|---|---|
| OpenStreetMap extract | Australia is the usual download (several hundred MB). I am not sure a ready-made NSW-only extract is published; if not, cut NSW out with a standard tool (`osmium`). |
| One-off import | Several minutes and 2 to 4 GB of memory for NSW with car and foot profiles. Run as a separate command, not at service start. |
| Graph on disk | Roughly 0.5 to 1.5 GB. |
| Memory while serving | Use memory-mapped storage so the graph sits in the operating system's file cache, not the Java heap. Heap need stays small; the file cache can be reclaimed under pressure, at the cost of slower queries. |
| Query speed | A few milliseconds per car route with the speed-up index built. |

OpenStreetMap data needs attribution under its licence (ODbL); the web app must show it wherever road results appear.

### 7.4 What the driving figure means

Drive times from OpenStreetMap are free-flow: no congestion. Compared with a timetable at 8 am, the car will look better than it is. The first version returns the free-flow time and labels it as such. An optional multiplier by time of day (a small table in configuration) is the cheap next step; real traffic data is out of scope. Parking and walking to the car are not included; a fixed allowance can be set in configuration (default 0).

### 7.5 The same engine for walking, and for the editor

- **Walking for RAPTOR: yes, in a later phase.** Replace straight-line transfer and access times with foot-network times, computed once at load for stop pairs within the radius. Straight-line stays as the fallback so the router never depends on road data.
- **Replacing the public OSRM server in the editor: yes, in a later phase.** Add three OSRM-shaped endpoints matching exactly what `apps/api/src/roads.ts` calls (`route`, `table`, `nearest`), so `ROUTER_URL` can point at the router with no editor change. After that, an "avoid this area" option would let `routedAround` in `roads.ts`, which searches for a detour by trial, be replaced by one request. This removes the item "a self-hosted routing server" and "a routing server that can be told a road is closed" from `PLAN.md`'s remaining work.

## 8. The service API

Base path `/v1`. JSON throughout. Stop and trip ids are GTFS ids (`gtfs_id` in the editor's tables), because those are what the export carries and what stays stable across edits.

### 8.1 Endpoints

| Method and path | Purpose |
|---|---|
| `GET /v1/health` | Up or not; which timetables are loaded; whether road routing is available. |
| `GET /v1/timetables` | List loaded timetables with version, counts and memory. |
| `GET /v1/timetables/{id}` | Metadata: service date, counts of stops, patterns, trips, stop times and transfers; transfer settings used; how many trips have placeholder or defaulted capacity; load time; memory. |
| `PUT /v1/timetables/{id}` | Load or reload. Body names the source: a URL to fetch a zip from (for example the editor's export address), a file path, or an uploaded zip. Returns at once with a build status; poll the metadata address. |
| `DELETE /v1/timetables/{id}` | Unload. |
| `POST /v1/journeys` | One journey query. |
| `POST /v1/journeys/bulk` | Many queries; results streamed. |
| `POST /v1/timetables/{id}/loads` | Create a named load state (empty, or from an uploaded CSV). |
| `GET /v1/timetables/{id}/loads/{name}` | Summary, or the full loads as CSV. |
| `DELETE /v1/timetables/{id}/loads/{name}` | Discard. |
| `POST /v1/road/route` | One driving (or walking) route. |
| `POST /v1/road/bulk` | Many road routes; results streamed. |

### 8.2 Single journey

Request:

```json
{
  "timetable": "b1-s7",
  "from": { "stop": "200060" },
  "to": { "lat": -33.8915, "lon": 151.2767 },
  "depart": "07:45:00",
  "capacity": { "mode": "check", "loads": "am-peak", "fullAt": 1.0 },
  "maxRides": 8,
  "maxWalkMetres": 800,
  "detail": "legs"
}
```

- `from` and `to` each take a stop id, a station id or a coordinate.
- `capacity.mode` is `off` (the default), `check` or `assign`. `loads` names a load state; it is required for `check` and `assign`.
- `detail` is `summary` or `legs`.

Response:

```json
{
  "timetable": { "id": "b1-s7", "version": "s7-h12-2026-11-13T04:10:22Z" },
  "capacityMode": "check",
  "status": "ok",
  "journeys": [
    {
      "label": "fastest",
      "depart": 27900, "arrive": 30120, "durationSecs": 2220,
      "rides": 2, "walkSecs": 420, "waitSecs": 300,
      "legs": [
        { "type": "walk", "from": {"lat": -33.88, "lon": 151.20}, "to": {"stop": "200060", "name": "..."},
          "depart": 27900, "arrive": 28080, "metres": 180 },
        { "type": "ride", "trip": "1--B.860.117.60.B.8.92804105", "route": "T4", "mode": "train", "headsign": "...",
          "board": {"stop": "200060", "name": "...", "time": 28200, "sequence": 5},
          "alight": {"stop": "2022...", "name": "...", "time": 28980, "sequence": 9},
          "stops": [ {"stop": "...", "lat": 0, "lon": 0, "arrive": 0, "depart": 0} ],
          "crowding": {"peakLoad": 912, "capacity": 1200, "peakFactor": 0.76, "capacityIsPlaceholder": true},
          "skippedFullTrips": 1, "stayAboard": false },
        { "type": "transfer", "depart": 28980, "arrive": 29100, "metres": 90 },
        { "type": "ride", "...": "..." }
      ]
    },
    { "label": "fewerChanges", "...": "..." }
  ],
  "computeMicros": 4200
}
```

- `status` is `ok`, `noJourney` or `stranded` (capacity left no way through), with a `reason`.
- `crowding` appears only when a load state was used. `skippedFullTrips` counts trips passed over because they were full.
- Ride legs list their intermediate stops with coordinates so the map can draw the leg. The exact path along the line is not returned; the web app already has line shapes.

### 8.3 Bulk

Request: the same fields as a single query, with shared settings once and the pairs as a list. Each pair carries an `id` chosen by the caller (for tap data, the record id), origin, destination, departure time and optional group size.

```json
{
  "timetable": "b1",
  "capacity": { "mode": "assign", "loads": "run-1" },
  "detail": "summary",
  "queries": [
    { "id": "a1", "from": {"stop": "200060"}, "to": {"stop": "2000336"}, "depart": 27900 },
    { "id": "a2", "from": {"stop": "2150101"}, "to": {"stop": "200060"}, "depart": 28020, "group": 2 }
  ]
}
```

Response: newline-delimited JSON, one line per query as it is finished, each carrying its `id`, then a final summary line (counts by status, re-routed, stranded, elapsed time, queries per second).

- **Synchronous and streamed** in the first version. Limit 200,000 queries per request (configurable); beyond that the caller splits the work. One `assign` run at a time per load state.
- In `off` and `check`, order of results is not guaranteed; in `assign`, processing follows the rule in section 4.2 and is repeatable.
- `detail: "summary"` returns times, ride count and the trips and stops used, without intermediate stops, to keep the stream small.
- **Job-based bulk** (submit, poll, download a compressed file; CSV input) is a later phase. It becomes necessary for a whole day of tap data, which I would expect to be in the millions of records for Sydney (not checked).

### 8.4 Road route

Request: `{ "from": {"lat":..,"lon":..}, "to": {..}, "profile": "car", "depart": "07:45:00" }`. Stop ids are accepted too when a timetable is named.

Response: `{ "status": "ok", "profile": "car", "metres": 14200, "durationSecs": 1260, "freeFlow": true, "geometry": [[lon,lat],...] }`.

`depart` is used only if a time-of-day multiplier is configured. The public transport and road endpoints are kept separate, as asked; the Node API or web app calls both and compares.

### 8.5 As a Java library

The modules are published as ordinary jars. The core has no web or road dependencies. Intended use, in outline:

```java
Timetable timetable = GtfsLoader.load(zipPath, LoadOptions.defaults());
Router router = new Router(timetable);            // safe to share between threads
LoadState loads = LoadState.empty(timetable);     // only for check / assign
Result result = router.route(query, CapacityMode.CHECK, loads);
```

The HTTP service is a thin layer over exactly these calls, so both routes into the code are tested by the same tests.

### What differs from the plan

- **Fewer patterns than the editor has.** The editor's 18,167 patterns are per route. The router groups by stops and pick-up and set-down flags only, so two routes over the same stops share a pattern, and the route is kept per trip. That is the likely reason the count is lower even after overtaking trips are split apart; the two effects were not counted separately.
- **Most "stations" are a single bus stop.** The feed gives 77,665 of the 89,444 stops a parent, so "station" does not mean a railway station. 67,179 parents have one stop in use and 9,990 have two. Checked in phase 2: of 16,341 pairs sharing a parent, 68 are more than 400 m apart, and the worst is 667 km (a mistake in the feed). Pairs more than 1 km apart are no longer linked as one station (a setting); that drops 8 pairs.
- **Block links work as planned.** 2,154 trips share a `block_id`, in 1,077 blocks of two trips each. 1,076 of the first trips run on into the second from the stop where they end, so the figure of "half" is only because the second trip of a pair has nothing to run on into. One block's second trip starts 571 m away and is not linked.
- **Every capacity is a placeholder,** as section 2 said: 59,014 of 59,014 trips. None needed the per-mode default.
- **Stops and stop names are plain text objects,** not one byte block as section 5 proposed. The whole timetable is 57 MB, so the saving was not worth the code.
- **The snapshot is keyed by the zip's contents** (SHA-256), the load options and the snapshot format, so a copy of the same zip reuses it and a changed setting does not.

### Decisions the plan left open

| Topic | What was built |
|---|---|
| Service date | Taken from the feed when it covers one day, as the editor's export does. An ordinary feed needs `--date`. |
| Times a feed leaves out | A stop with no time is spread evenly between its timed neighbours. A trip is left out if it has fewer than two stops, no time at either end, or times that go backwards. None of this happens in the editor's export. |
| Pick-up and set-down | Only type 1 ("none") blocks boarding or leaving. Types 2 and 3 (phone or ask the driver) count as allowed. |
| Which link wins for one pair of stops | `transfers.txt`, then pathways, then same station, then distance. A pathway time is used even when the straight-line walk would be quicker. |
| Limit per stop | Applies to generated links only. Links from pathways and `transfers.txt` are always kept. |
| Walks through a station | Not offered beyond 900 s. A pathway with no time is taken as 60 s. Both are settings. |
| `transfers.txt` | Rows for one route or trip, and rows that name a station, are left out and counted. The editor's export has no such file, so this is tested on hand-made feeds only. |
| Default capacity by mode | Train 1,200, metro 1,100, light rail 300, ferry 400, bus 65, coach 50, school bus 70: the editor's placeholder types. |

### Speed, roughly

One run of 3,000 random stop-to-stop queries on the weekday, one thread, up to 8 rides, departure times from 05:00 to 22:00. This is not the benchmark of section 10.2: the pairs are uniform over all 89,444 stops in NSW, not weighted by service.

| Measure | Target (section 10.3) | Measured |
|---|---|---|
| Median | under 10 ms | 11.4 ms |
| 95th percentile | under 30 ms | 64.2 ms |
| 99th percentile | not set | 85.0 ms |
| Queries per second | over 1,000 on 8 threads | 49 on one thread |
| Queries with an answer | not set | 25% |

Both time targets are missed on this mix. An average query scanned 15,724 patterns over its rounds, against 17,976 in the timetable, so most queries explored much of the state. Only a quarter had an answer; a query with no answer has nothing to prune against and runs every round. I have not checked why so few have an answer; school-only stops and regional networks with no link to the rest are the likely reasons. Tuning is phase 5, where the service-weighted query set will show whether the targets are in reach. One candidate is to bound the search by time (for example, give up 6 hours after departure).

### What differs from the plan

- **Two arrival times per stop per round, not one.** The plan's walking links do not chain: A to B and B to C does not give A to C. A passenger who arrives at a stop on foot may board there but may not walk on, so "arrived on a vehicle" and "arrived on foot" are kept apart. One number would either lose journeys or allow two walks in a row. The cost is 16 MB of working memory per thread, against the 12 MB estimated.
- **Stay-aboard uses up a ride.** As section 6.2 said for the first version: two trips on one vehicle count as two rides against the limit of 8, and as no change in the result.
- **A stop as origin includes the stops one walk away,** so a journey from a stop may start with a walk to the stop across the road. The same holds at the destination.
- **Walking the whole way** is offered when the two ends are one walking link apart, or two points within the walking limit. It is labelled `walk`.
- **The journey's departure is the time asked for,** not the latest time the passenger could leave and still catch the first vehicle. Waiting at the first stop counts as waiting.
- **Walks from a point** use the walking speed and detour factor without the fixed 30 seconds, as section 6.3 says.

### Not done in phase 2

- The simulator's request options (section 4.4): a query can start from a given stop at a given time, but blocked boardings are left for phase 4, where they are first needed.
- A minimum time to change at one stop. A change at the same stop takes no time.
- Leaving a mode out per request (question 15).

## 17. Quality and speed of results (15 Nov 2026)

Done before phase 3, at the owner's request. Test journeys are now drawn only inside the Opal area: a rectangle from the Hunter and Newcastle in the north to Wollongong and Kiama in the south, west to the Blue Mountains (latitude -34.75 to -32.70, longitude 150.10 to 151.85). Each end is a stop picked in proportion to how many times a vehicle calls there in the day, and departure times lean towards the two peaks, as section 10.2 asks. `npm run router:route -- "-ProuteArgs=--random 3000"` runs it; `--within <km>` limits how far apart the ends are, `--show <n>` prints journeys to read, `--area all` goes back to the whole state.

### Quality: what was wrong and what changed

Found by reading sample journeys. Each has a test on the hand-made feed.

| Problem | Change |
|---|---|
| A journey was shown leaving at the time asked for, then waiting at the first stop, sometimes for hours. | The journey now leaves as late as it can. Working back from the last ride, each earlier ride moves to the latest trip of the same pattern that still makes the connection, and the first walk is timed to meet the first vehicle. Arrival is unchanged. On average the passenger can leave 7 minutes after the time asked for. |
| Alternatives with fewer changes were offered however much slower they were. One waited over four hours to save a change. | An alternative is offered only if it arrives no more than 30 minutes later for each ride it saves (a setting). |
| The fastest journey was always first, even when it used two more vehicles to save a minute. | The result names a recommended journey: the fastest, unless one with fewer boardings is within 5 minutes per boarding saved (a setting). It differs from the fastest in about 14% of journeys. |
| Walking links were missing at the largest interchanges, because of the limit of 40 per stop. A journey to Central's Railway Square left the metro at Martin Place for two buses instead of riding to Central and walking. | The limit is now 150. No stop reaches it (the most is 54), so nothing is cut. That journey now arrives 6 minutes sooner with two fewer vehicles. |
| School buses could not be left out. They are in about 7% of recommended journeys. | A query can avoid kinds of vehicle (`--avoid school_bus`). A pattern now holds one kind of vehicle only, so avoided patterns are skipped whole. They are still included by default: see the question below. |
| Two stops of one "station" 667 km apart were linked. | Fixed earlier: stops of one station more than 1 km apart are not linked as one. |

Not changed: journeys are still the earliest arrival for each number of rides. Nothing prefers less walking, or one mode over another, beyond the rules above.

**Question for the owner (extends question 15):** should school buses be left out unless asked for? The default is still to include them, as question 15 says.

### Speed

Measured on the development machine (6 cores, 256 KB of fast cache per core, other programs running). 3,000 test journeys per row; each timed four times and the quickest kept; then all run together on 6 threads.

| Test journeys | Asked time to arrival | Median | 95th percentile | Per second, 1 thread | Per second, 6 threads |
|---|---|---|---|---|---|
| Ends within 10 km | 48 min | 0.80 ms | 4.7 ms | 702 | 1,941 |
| Ends within 25 km | 72 min | 3.05 ms | 11.3 ms | 245 | 683 |
| Any two stops in the area | 123 min | 8.28 ms | 18.6 ms | 114 | 326 |

Against section 10.3: the single-query targets (median under 10 ms, 95th percentile under 30 ms) are met on all three. The bulk target (over 1,000 a second on 8 threads) is met for journeys within 10 km and missed for longer ones. I have no tap data to say which row real trips resemble.

What the work changed, on the same journeys: any two stops went from a median of 9.1 ms to 8.3 ms; ends within 25 km from 3.9 ms to 3.0 ms; ends within 10 km from about 1.0 ms to 0.8 ms. Those are modest gains for seven changes, all of which keep the answers exact (the brute-force check still passes):

- board only at stops reached earlier in the previous round;
- do not ride a trip again that an earlier round has already ridden from the same stop or before;
- stop riding a trip once it is past the last stop worth boarding at and already later than the best arrival found;
- skip stops and walks that are already later than the best arrival found;
- stops numbered by map position, and the search's numbers for a stop, a pattern and a walking link each kept together, so they come from memory in fewer fetches.

Why it is not faster: a search costs in proportion to how much of the network can be reached before the destination is. For a two-hour journey that is most of the Opal area: about 17,000 pattern scans, 26,000 improved arrivals and 190,000 walking links looked at. Six threads give about three times one thread, not six, which I take to be this machine's shared memory and not the code; I have not confirmed that on another machine.

What would make long journeys much faster, none of it done:

- A limit on how far ahead of the best-known arrival the search looks. Simple, but no longer exact for the fewer-changes alternatives.
- Pruning by a lower bound on the time still needed to reach the destination. Needs a bound that is provably safe; straight-line distance over a top speed is not, because timetables have stops a zero-minute hop apart.
- Range RAPTOR for bulk runs without capacity (already in phase 8).

## 18. Compared with the TfNSW trip planner (15 Nov 2026)

300 test journeys inside the Opal area (200 with ends within 25 km, 100 between any two stops) were asked of the TfNSW Trip Planner API for the same service day, Tuesday 17 Nov 2026, and compared with ours. To repeat it:


TfNSW's answers are kept beside the input, so a second run asks nothing again. The full report, journey by journey, is written beside it as `.report.txt`.

**How the two were made comparable.** Both planners go between the map positions of two stops, not the stops themselves. Asked for a stop, TfNSW boards only at that stop: it answered some journeys hours late where a 300 m walk to a station would have done. Asked for a position, it snaps to the nearest street address and walks along paths, so its walks at the two ends differ from ours by a few minutes either way. Differences of a few minutes are therefore mostly noise.

### What the comparison found wrong with ours, and the fix

Our journeys changed vehicles at one stop with no time to spare: off one bus and onto another in the same second. In 769 changes at one stop in TfNSW's answers, none was under 2 minutes. **A change at one stop now takes at least 2 minutes** (`changeSecs`, a setting of the query; `--change <secs>` on the command line). A walk to another stop still takes the link's own time, and staying aboard a vehicle that runs on as another trip takes none. The search stays exact: the brute-force check now includes this rule and vehicles that run on, and passes on 10,000 queries. Speed is unchanged (median 3.2 ms within 25 km, 8.6 ms for any two stops).

### What differs from the plan

- **Each timetable has its own planning threads.** Section 9 has one fixed pool. A search keeps about 16 MB of working memory per thread per timetable, held by the thread, and it is only given back when the thread ends. So a timetable's threads end when it is unloaded or replaced; journeys already being planned on it finish first.
- **One build at a time.** A build is the most memory the service uses. A second load request for an id that is still building is refused (`409`); for another id it waits its turn.
- **`position`, not `sequence`.** Section 8.2 gives each boarding and alighting stop its `stop_sequence`. The timetable does not keep that number, so the answer gives the stop's place in the trip, counting from 0.
- **More in a request than section 8.2 lists:** `avoid`, `changeSecs` and `lessWalking`, for the settings added in sections 17 and 18. `timetable` may be left out when one is loaded.
- **More in an answer:** `recommended` (which journey to suggest), `changes`, and `routeId` beside the route's name.
- **A `stop` that names a station is taken as the station.** Most "stations" in this feed are a single bus stop (section 15), and a caller with an id cannot tell which it holds.
- **The version is whatever the caller says it is.** The router does not work out the key of section 6.5; the Node API will, in phase 7. Left out, it is the time of the request.
- **Old snapshots of fetched and uploaded zips are removed** when a newer one is built for the same id. Snapshots of zips loaded by path are still never removed.
- **`ROUTER_LOAD`** loads timetables at start. The plan did not have it.

### Not done in phase 3

- **The Docker image was not built or run.** Docker was not running on the development machine. The `Dockerfile` and `docker-compose.yml` were changed for the data folder and are untested.
- No access control (question 14). The load request reads any file the service can read and fetches any URL it is given.
- A request for capacity mode `check` or `assign` is refused (`501`) until phase 4.
- A journey whose caller goes away is still planned to the end.
- The export without shapes (section 6.1) is not built, so loading by URL from the editor still waits two to five minutes for the export.

## 20. Phase 4 findings (17 Nov 2026)

Phase 4 is built: load states, the capacity switch (`off`, `check`, `assign`) on one journey and on many, the bulk endpoint, and the load-state endpoints. The requests and answers are described in `services/router/README.md`. Of the endpoints in section 8.1 only the two road ones remain.

### How it was checked

| Check | Result |
|---|---|
| Brute-force reference with full vehicles | 15,000 random queries on 600 small random timetables, with trips full for all or part of their run, groups of 1 to 3, trips counted full at 90% in a quarter of queries, and up to 3 refused boardings. The search and the simple search agree on the earliest arrival for every limit on rides, and on whether a passenger is stranded. Every journey replays, including that each vehicle boarded had room. |
| `check` with empty loads equals `off` | 5,000 random queries on random timetables give the same journeys. On the real weekday, 3,000 journeys (the 300 saved test journeys of section 18, ten times) give the same arrival in every one. |

### Speed, roughly

Not the benchmark of section 10.2, which is phase 5. One bulk request each on the development machine, with other programs running; the 300 saved test journeys repeated. Runs of the same thing varied by 10 to 15%.

| Run | Per second |
|---|---|
| `off`, 3,000 journeys, three runs | 706, 733, 637 |
| `check` on empty loads, the same journeys, run alternately with those | 654, 621, 578 |
| `check` on the loads the assignment below left | 546 against 569 for `off` just before; 386 against 410 |
| `assign`, 6,000 requests of 5 passengers | 257 |

- **`check` on empty loads is about 11% slower than `off`** (the target of section 10.3 is under 10%). Part of that is reporting crowding on every ride, not the search.
- **`check` on realistic loads was about 5% slower than `off`**, inside the 30% target.
- **`assign` ran at 257 a second, under the target of 500.** A third of the requests (1,987) were routed again, one at a time, because the test puts 100 passengers on one pair of stops at one moment and a bus holds 65. 120 requests were stranded. Demand shaped like real travel should re-route far less; phase 5's demand generator will say.

### What differs from the plan

- **A passenger who does not fit is routed again at once,** against the loads as they then stand, not held back to be routed with the others who did not fit. The second try then nearly always fits, and the answer is still the same for any number of threads.
- **A CSV of loads gives `position`, not `stop_sequence`:** the stop's place in the trip, counting from 0. The timetable does not keep `stop_sequence` (section 19).
- **A bulk line carries one journey,** the recommended one, and no alternatives. `detail` is `summary` in a bulk request unless it says otherwise.
- **In `off` and `check` the lines are in the order asked,** which section 8.3 did not promise.
- **A query that cannot be planned does not fail the request.** It gets a line with `"status": "error"`.
- **The body of a bulk request is read a query at a time,** so 200,000 queries do not have to be held as text. The answers are not held at all.
- **`group` and `blocked` are accepted on a single journey too.** `blocked` is the simulator's option of section 4.4; it names a trip and a stop.
- **Stay-aboard under load.** A passenger aboard a vehicle that runs on as another trip stays aboard even if that trip is full for anyone boarding. The plan did not say. It makes those patterns slower to search with loads, because a later trip with room only further along may be the only way onto a full onward trip; 1,076 of the weekday's 59,014 trips run on.
- **`stranded` costs a second search.** When loads leave no journey, the search runs again without them to tell `stranded` from `noJourney`.
- **A timetable holds at most 8 load states,** each 8 MB for the weekday.

### Not done in phase 4

- The optional second pass of section 4.2 (empty the loads and assign everyone again until routes settle). The plan recommends leaving it until the simulator shows a need.
- Crowding as a penalty (section 4.3). `fullAt` is the "comfortable capacity" option of that section.
- Load states are kept in memory only. They are lost when the service stops or the timetable is reloaded.
- A bulk request is answered while the caller waits. Jobs (submit, poll, download) are phase 8.
- The Docker image is still not built or run.
- One suspicion not followed up, in the search without loads: when a vehicle runs on twice in a row (three trips in one block), the search may offer staying aboard a trip the passenger could not have been on. The brute-force check has not caught it in 10,000 queries, and the weekday has no block of more than two trips.
